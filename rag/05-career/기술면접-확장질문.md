# 기술면접 확장질문 — 프로젝트 주변의 지식 방어선 23문항

> 위치: [면접-관문질문](면접-관문질문.md) 16개가 **본진**(프로젝트 딥다이브)이고, 이 문서는 그 주변을 두르는 **기초 지식 방어선**입니다. 순서를 지키세요 — 관문 16개를 소리 내어 답할 수 있게 된 뒤(W12) 이 문서로 넘어옵니다.
> 형식은 관문질문과 동일: 모범답안 없이 **① 좋은 답의 필수 요소 ② 내 프로젝트에서 가져올 증거 ③ 예상 꼬리질문**.
> 답변 공식도 동일: **정의 한 줄 → 내 경험/숫자 → 트레이드오프 → (여유 되면) 다음 단계.**

⚠️ **코딩테스트는 이 문서 범위 밖입니다.** 회사에 따라 프로그래머스/백준식 코테가 있으니 W12 JD 분석 때 지원 대상 회사들의 전형을 먼저 확인하고, 필요하면 지원 직전 2~3주를 따로 배정하세요 (12주 계획과 병행 금지 — 셋 다 얕아집니다).

## A. 인공 신경망 — 근거 문서: [08-신경망-기초](../01-basics/08-신경망-기초.md)

### A1. 인공 신경망이 뭔가요? 뉴런 하나는 무슨 계산을 하나요?
- **필수 요소**: 가중합+편향+활성화 한 줄 / "패턴 감지기를 병렬(층)·직렬(깊이)로 조합한 함수" / 학습이 조정하는 건 가중치
- **내 증거**: "제 bigram은 은닉층 0개짜리 퇴화형이라, 층이 왜 필요한지를 그 한계(loss 정체)로 체감했습니다"
- **꼬리**: "층을 쌓으면 왜 좋아지나요?" (단순 패턴 → 조합 패턴의 단계적 감지)

### A2. 활성화 함수는 왜 필요한가요? ReLU를 많이 쓰는 이유는?
- **필수 요소**: 선형의 합성은 선형 — 없으면 100층도 직선 하나 / ReLU: 싸고, 기울기가 안 죽음(sigmoid의 기울기 소실과 대비)
- **꼬리**: "sigmoid는 언제 쓰나요?" (0~1 출력이 필요한 곳), "GPT는 뭘 쓰나요?" (GELU 계열 — 이름만)

### A3. 역전파를 설명해보세요
- **필수 요소**: "오차의 책임을 출력→입력 방향으로 연쇄법칙으로 배분해 각 파라미터의 기울기를 구한다" / forward→backward→step의 위치 / autograd가 대신해준다는 실무 감각
- **내 증거**: zero_grad 누락으로 기울기가 누적되는 버그를 직접 겪은 경험 (겪었다면!)
- **꼬리**: "기울기 소실이 뭔가요?" (연쇄 곱이 0으로 → 잔차 연결이 해결)

### A4. 과적합이 뭐고 어떻게 막나요?
- **필수 요소**: train↓ val↑의 정의 / 도구 3종: dropout·weight decay(AdamW의 W)·early stopping / 근본 해결은 데이터
- **내 증거**: W7에 데이터를 1/100로 줄여 **일부러 과적합을 만들어본** 실험 — "본 적 있는" 사람의 답은 다릅니다

## B. 평가지표 — 근거 문서: [평가지표-완전정복](../04-concepts/평가지표-완전정복.md)

### B5. precision과 recall의 차이를 예를 들어 설명해보세요
- **필수 요소**: "내가 가져온 것 중 진짜(P) vs 진짜 중 가져온 것(R)" / 자기 도메인 예시 (검색 top-k)
- **내 증거**: "hit@3는 제 골든셋 구조상 recall@3와 같고, precision 방향은 답 없는 질문 5개로 따로 측정했습니다"

### B6. accuracy만 보면 왜 위험한가요? F1은 왜 조화평균인가요?
- **필수 요소**: 불균형 데이터 예시 (35문항 중 no_answer 5 → 다 "있음"이라 해도 86%) / 조화평균은 낮은 쪽에 끌려가 둘 다 좋아야 높음 (P=1.0, R=0.01 → F1≈0.02 손계산)

### B7. top-k를 키우면 recall과 precision은 각각 어떻게 되나요?
- **필수 요소**: k는 recall을 사고 precision을 파는 손잡이 / RAG에선 프롬프트 노이즈 → 생성 품질로 이어짐
- **내 증거**: 실험④의 실제 숫자 — 관문질문 4번의 지표 언어 버전이므로 두 답을 연결해 준비

## C. LLM 학습 — 근거 문서: [LLM학습-3단계](../04-concepts/LLM학습-3단계.md)

### C8. base 모델과 instruct(chat) 모델의 차이는?
- **필수 요소**: base = 이어쓰기 기계 / instruct = SFT로 지시-답변 형식을 학습한 것
- **내 증거**: "제 tiny 모델이 정확히 base 상태라 질문에 답하지 않고 이어 씁니다 — 그 경험으로 차이를 설명할 수 있습니다"

### C9. GPT는 왜 지시를 따르나요? (SFT와 RLHF는 각각 무엇을 바꾸나요?)
- **필수 요소**: 3단계 흐름 / SFT는 **같은 next-token 학습에 데이터만 지시-답변 쌍**이라는 통찰 / RLHF·DPO는 사람 선호 반영 단계

### C10. LoRA가 뭐고 왜 쓰나요?
- **필수 요소**: 원본 가중치 동결 + 작은 어댑터만 학습 / full FT 대비 비용이 수백분의 1 / PEFT라는 상위 개념
- **꼬리**: "quantization과는 뭐가 다른가요?" (LoRA는 학습 효율화, 양자화는 실행 압축)

### C11. 내 서비스에 지식을 넣을 때 RAG와 파인튜닝 중 뭘 고르나요?
- **필수 요소**: **지식은 RAG, 형식·말투는 SFT** / 갱신 주기·출처 표시 요구가 결정 변수
- **내 증거**: "매주 갱신되는 공고문이라 파인튜닝으로는 따라갈 수 없어 RAG를 선택" — 관문질문과 겹치는 핵심 카드

## D. Transformer 심화 — 근거 문서: [어텐션-개념](../04-concepts/어텐션-개념.md) 7·8절

### D12. attention은 토큰 순서를 어떻게 아나요?
- **필수 요소**: attention 자체는 순서를 모름(가중평균은 집합 연산) / positional encoding을 embedding에 더해 위치를 주입 / RoPE 등은 이름만
- **내 증거**: "bigram은 '직전 1개'라는 구조에 순서가 내장돼 있어 필요 없었는데, 전부 보는 attention이 되는 순간 왜 필요한지가 명확해졌습니다"

### D13. BERT와 GPT의 차이는? 임베딩 모델은 왜 BERT 계열인가요?
- **필수 요소**: 인코더(양방향, 이해→벡터) vs 디코더(단방향 causal, 생성) / 학습 목표 차이 (빈칸 맞히기 vs 다음 토큰)
- **내 증거**: **두 프로젝트가 정확히 이 두 갈래** — gongo-rag의 ko-sroberta(BERT계)와 tiny(GPT계)를 둘 다 만져봤다는 희귀한 포지션

### D14. context window는 왜 무한정 못 늘리나요?
- **필수 요소**: 모든 토큰 쌍의 Q·K 계산 → 길이의 제곱 비용 / 그래서 RAG가 필요하다는 순환 완성 / (여유 되면) KV cache: 생성 시 이전 토큰의 K·V를 재계산 않고 저장해두는 서빙 최적화 — 이름과 역할만

## E. 에이전트 / Tool Calling

> **미니 개념** (별도 문서 없음, 이 박스가 교과서):
> **Function calling(tool use)** — 개발자가 "사용 가능한 함수 목록과 파라미터 형식"을 모델에 알려주면, 모델이 답 대신 `{"name": "search_gongo", "arguments": {"query": "신청 자격"}}` 같은 **구조화된 호출 요청**을 출력 → 내 코드가 실행 → 결과를 대화에 다시 넣어 최종 답 생성.
> **에이전트** — 이 도구 호출을 목표 달성까지 **반복하는 루프** (관찰→판단→도구 실행→다시 판단). 고정 파이프라인과의 차이: 순서를 모델이 결정한다.

### E15. function calling이 뭔가요?
- **필수 요소**: 위 정의 / "모델은 실행하지 않는다, 호출을 제안할 뿐 실행은 내 코드" — 이 경계를 아는 게 실무 감각

### E16. RAG와 에이전트의 관계는?
- **필수 요소**: 내 RAG는 고정 순서(항상 검색→생성), 에이전트에선 **검색이 도구 중 하나**가 되고 모델이 검색 여부·횟수·질의 변형을 결정
- **내 증거**: "gongo-rag를 에이전트로 확장한다면 — 검색을 tool로 등록하고, 결과가 부족하면 모델이 질의를 바꿔 재검색하게 하겠다. 다만 평가가 어려워지므로 지금 규모에선 고정 파이프라인이 낫다고 판단했다" ← 확장 방향과 절제를 동시에 보여주는 답

## F. 서빙 / 프로덕션

> **미니 개념**:
> **지연(latency)** = 첫 토큰까지의 시간 + 토큰당 생성 속도. **streaming**은 총 시간을 줄이진 않지만 첫 글자를 바로 보여줘 체감을 바꿈.
> **비용** = 입·출력 토큰 수 — top-k와 chunk 크기가 곧 돈.
> 프로덕션에서 추가되는 것: API 서버(**FastAPI**), 키 보안(서버에서만 호출), 로깅·모니터링(실패 케이스 자동 수집), 캐싱(동일 질문 재사용), 평가 자동화(골든셋을 배포 전 회귀 테스트처럼).
> **Docker** 한 줄: "제 컴퓨터에선 되는데요"를 없애는 실행 환경 포장.

### F17. LLM 응답이 느리면 무엇을 보겠어요?
- **필수 요소**: 프롬프트 길이(top-k·chunk 크기!) → 모델 크기 → streaming 적용 → 캐싱 순의 점검 리스트
- **내 증거**: "top-k 실험에서 k가 품질뿐 아니라 토큰량(=지연·비용)을 늘리는 것도 기록했습니다"

### F18. 이 데모를 실서비스로 만들면 뭐가 달라지나요?
- **필수 요소**: 위 미니 개념의 목록을 자기 말로 / **정직 프레임**: "서빙 운영 경험은 아직 없지만, 무엇이 추가되어야 하는지의 지도는 있고 빠르게 배울 접점(웹 퍼블리셔로서 HTTP/프론트 이해)이 있습니다"
- 모르는 걸 아는 척하는 것보다 이 정직+지도 조합이 신입에겐 훨씬 강합니다

### F19. Docker는 왜 쓰나요?
- **필수 요소**: 실행 환경 통째 포장 → 어디서나 동일 실행 / venv와의 차이(파이썬 패키지만 vs OS 수준까지) 한 줄이면 충분

## G. ML 일반

### G20. train/validation/test는 왜 나누나요? (당신은 val까지만 썼는데?)
- **필수 요소**: val은 튜닝하며 반복해서 보는 모의고사 → **하이퍼파라미터가 val에 과적합**될 수 있음 → 마지막에 딱 한 번 여는 게 test
- **내 증거**: "골든셋 35문항 규모에선 셋으로 나누면 각각이 통계적으로 무의미해져 val까지만 썼고, 이 한계를 인지하고 있다" — 한계를 아는 답이 만점

### G21. 데이터가 적을 때 무슨 문제가 생기고 어떻게 대처하나요?
- **필수 요소**: 과적합(tiny에서 직접 관찰) + 평가 신뢰도 하락(골든셋) / 대처: 데이터 증강·정규화 도구·**유형별 분석으로 적은 데이터에서 최대 정보 뽑기**
- **꼬리**: "bias-variance로 설명하면?" — 너무 단순한 모델=편향(제 bigram이 그 사례), 복잡한 모델+적은 데이터=분산(과적합). **내 두 프로젝트로 둘 다 예시 가능**

## H. 파이썬 / CS 가벼운 층

### H22. dict는 왜 검색이 빠른가요?
- **필수 요소**: 해시 — 키를 주소로 변환해 바로 접근, 평균 O(1) vs 리스트 순회 O(N)
- **내 증거**: "BM25의 df를 dict로 만든 이유입니다. 문서가 늘어도 단어 조회 비용이 일정하니까요"

### H23. 당신의 임베딩 검색은 문서가 100만 개면 어떻게 되나요?
- **필수 요소**: 지금은 전수 비교 O(N) — 수백 개면 밀리초, 수백만이면 병목 / 그때 **ANN**(근사 최근접 이웃, HNSW 같은 인덱스)으로 전환 — 정확도를 조금 내주고 속도를 크게 얻음 / 벡터 DB가 해주는 일이 바로 이것
- **내 증거**: "왜 벡터 DB를 안 썼나"(관문 대비)의 기술적 뼈대 — 규모·복잡도·도입 기준을 숫자로
