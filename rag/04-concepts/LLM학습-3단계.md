# LLM 학습 3단계 — 내 tiny 모델은 왜 지시를 안 따르는가

> 읽는 시점: Week 8~9 저녁 (attention 개념 이후). 선행: [사전훈련-원리](사전훈련-원리.md).
> 이 문서는 여러분이 직접 만든 것(1단계)과 API로 쓰는 것(3단계까지 끝난 모델) 사이의 빈칸을 채웁니다.

## 0. 출발점이 되는 직접 경험

여러분의 tiny 모델에게 "질문: 신청 자격은? 답변:"을 주면 답을 하는 게 아니라 **그 뒤에 올 법한 텍스트를 이어 쓸 뿐**입니다. GPT의 베이스 모델도 똑같습니다 — "프랑스의 수도는 무엇인가요?"라고 물으면 "독일의 수도는 무엇인가요? 스페인의 수도는…" 하고 **비슷한 문장을 이어 쓰기도** 합니다. 사전훈련의 목표가 "이어 쓰기"였으니 당연한 결과죠.

그런데 ChatGPT/Claude는 지시를 따릅니다. 그 사이에 두 단계가 더 있기 때문입니다.

```mermaid
flowchart LR
    A["① Pretraining<br/>대량 텍스트, next-token"] --> B["Base 모델<br/>'인터넷 이어쓰기 기계'"]
    B --> C["② SFT<br/>(지시→모범답변) 쌍으로 추가 학습"]
    C --> D["Instruct 모델<br/>'지시를 따르는 형식 습득'"]
    D --> E["③ 선호 정렬 RLHF/DPO<br/>사람이 고른 A/B 선호 반영"]
    E --> F["Chat 모델<br/>'유용하고 안전한 답'<br/>= 여러분이 API로 쓰는 것"]
```

## ① 1단계 — Pretraining (이미 직접 해봄)

- 목표: next-token prediction. 결과물: **base 모델**.
- 규모 감각: 수조 토큰 × GPU 수천 장 × 수개월. tiny와 원리는 같고 크기만 다름.
- 여기서 언어의 문법·사실·추론 능력의 **원재료**가 만들어짐. 단, "대화 상대"의 형식은 없음.

## ② 2단계 — SFT (Supervised Fine-Tuning, 지시 튜닝)

- 사람이 만든 **(지시, 모범 답변) 쌍** 수만~수십만 개로 base 모델을 추가 학습.
- **핵심 통찰: 학습 방식은 여전히 next-token prediction입니다.** 바뀐 건 데이터뿐 — "질문 다음엔 답변이 온다"는 형식의 텍스트만 집중적으로 보여주는 것. 여러분이 이미 아는 메커니즘 그대로입니다.
- 결과: 지시를 따르는 **instruct 모델**. 규모는 사전훈련의 수백~수천분의 1.

## ③ 3단계 — 선호 정렬 (RLHF / DPO)

SFT까지 해도 문제가 남습니다: 같은 지시에 가능한 답이 여럿인데, 어떤 답이 더 유용하고 안전한지는 "모범답안 따라쓰기"로 다 못 가르칩니다.

- 방법: 모델이 답 A와 B를 생성 → **사람이 더 나은 쪽을 선택** → 그 선호를 만족하도록 모델을 조정.
- **RLHF**: 선호 데이터로 "채점 모델(보상 모델)"을 만들고, 강화학습으로 점수가 높아지게 조정 (ChatGPT를 만든 방식).
- **DPO**: 보상 모델·강화학습 없이 선호 쌍으로 직접 학습하는 간소화 방식 (요즘 널리 쓰임).
- 면접에선 두 이름과 "사람의 선호를 반영하는 단계"라는 역할만 정확하면 충분합니다.

## ④ LoRA / PEFT — 파인튜닝의 실무 표준

"파인튜닝"이라고 하면 실무에서는 대부분 이것을 말합니다.

- 문제: 수십억 파라미터를 전부 다시 학습(full fine-tuning)하면 GPU 메모리와 비용이 감당 불가.
- **LoRA**: 원래 가중치는 **얼려두고**, 그 옆에 아주 작은 보조 행렬(어댑터)만 붙여 학습. 비유: 수천억 개 손잡이를 다 돌리는 대신, 옆에 작은 미세조정 손잡이 세트를 붙이는 것. 학습 파라미터가 수백분의 1로 줄어 단일 GPU로도 가능.
- **PEFT** = 이런 "일부만 효율적으로 학습" 기법들의 총칭 (LoRA가 대표).
- **Quantization(양자화)** 한 줄: 학습이 아니라 **실행**을 가볍게 — 파라미터를 16bit → 4bit 등으로 줄여 메모리를 아끼는 압축. 정확도를 약간 내주고 비용을 크게 아낌.

## ⑤ 그래서 RAG와 파인튜닝, 언제 뭘 쓰나 (선택 기준 완성판)

[02-LLM-기초](../01-basics/02-LLM-기초.md) 6번 표의 심화판:

| 바꾸고 싶은 것 | 도구 | 이유 |
|---|---|---|
| **지식** (우리 회사 문서, 최신 공고) | **RAG** | 문서 갈아끼우면 즉시 반영, 출처 표시 가능 |
| **형식·말투·도메인 스타일** (우리 서비스 어투, 특정 출력 포맷) | **SFT(LoRA)** | 예시로 형식을 각인시키는 문제라서 |
| **가치판단·안전성** | 선호 정렬 | 모델 제공사의 영역 (우리는 프롬프트로 보완) |
| 둘 다 | RAG + LoRA 병행 | 상호 배타적이지 않음 |

면접 답변 뼈대: "지식은 RAG로, 형식은 파인튜닝으로 — 공고문 Q&A는 지식 문제라서 RAG를 선택했고, 실제로 파인튜닝으로는 매주 갱신되는 공고를 따라갈 수 없습니다."

## ⑥ tiny와 다시 연결 (면접 킬러 멘트 재료)

> "사전훈련을 직접 구현해보니 base 모델이 왜 지시를 안 따르는지 몸으로 이해했습니다 — 목표 함수가 '이어 쓰기'니까요. 그래서 SFT가 데이터만 바꾼 같은 학습이라는 것, RLHF가 그 위의 선호 조정이라는 것이 자연스럽게 정리됐습니다."
