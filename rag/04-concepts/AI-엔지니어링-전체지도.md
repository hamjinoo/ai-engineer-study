# 🗺️ AI 엔지니어링 전체 지도 — 4개 영상 통합 정리

> LLM 원리 → RAG → 에이전트 → 프로덕션 운영까지, 영상 4개를 하나의 지도로 합친 문서.
> 현재 프로젝트의 전체 그림과 단일 체크리스트는 [RAG 전체지도](../RAG-전체지도.md), 이 문서는 더 넓은 AI 엔지니어링 개념을 찾아볼 때 사용한다.
> 작성: 2026-07-19

---

## 한 줄 핵심

4개 영상은 따로가 아니라 하나의 커리큘럼이다:

> **LLM이 어떻게 답을 만드는지 → 외부 지식을 검색하는 RAG → 도구를 선택해 행동하는 에이전트 → 실제 서비스로 안정적으로 운영하는 시스템 설계.**

| 영상 | 역할 |
|---|---|
| ① 포트폴리오 5종 | **실행 계획** — 뭘 만들어 증명할까 (→ 로드맵으로 변환 완료) |
| ② 전체 지도 (LLM→평가) | **지도** — 이 동네에 뭐가 있나 |
| ③ RAG 심화 (10패턴) | **확대경** — 내가 서 있는 동네 확대 |
| ④ 프로덕션 시스템 설계 | **현미경** — 동네에서 사는 것 vs 동네를 운영하는 것 |

## 전부를 관통하는 두 문장

**1. "모델을 믿지 말고, 시스템으로 감싸라."**
LLM은 확률적 자동완성기라 언제든 틀린다(②) → 근거를 검색해 붙이고(③) → 출력을 스키마로 묶어 검증·재시도하고, 위험한 행동은 코드와 사람이 최종 판단하고(④) → 전부를 숫자로 감시한다(①④).
같은 말: **"비즈니스 규칙의 최종 판단자는 에이전트가 아니라 애플리케이션 코드다."**
안정성이란 모델을 완벽하게 만드는 게 아니라, **모델이 실수할 것을 가정하고 그 실수가 제품 실패로 이어지지 않게 설계하는 것.**

**2. "평가가 척추다."**
②의 종착지 = evaluation. ③의 결론 = "패턴보다 측정 먼저". ④의 핵심 = trace-level 평가. ①의 차별점 = 골든셋+CI.
→ 넷이 전부 [evaluate.py](https://github.com/hamjinoo/gongo-rag/blob/main/src/evaluate.py)가 하는 일로 수렴한다.

## 사람 비유로 외우는 전체 구조

```text
LLM            = 두뇌
컨텍스트       = 지금 책상 위에 놓인 자료
RAG            = 필요한 자료를 찾아오는 능력
도구           = 손과 발
메모리         = 과거에 기억해 둔 정보
상태           = 현재 일이 어디까지 진행됐는지
오케스트레이션 = 전체 작업 순서를 통제하는 관리자
평가           = 일을 제대로 했는지 검사하는 시험
관측 가능성    = 어디서 실패했는지 볼 수 있는 기록
```

실제 AI 제품 = LLM 하나가 아니라 **이 요소들을 조립한 소프트웨어 시스템.**

# 6층 지도

```text
[6층] 평가·관측   ← 모든 층을 관통하는 척추
[5층] 운영·통제   ← 라우팅, 계약, 승인, 보안, 비용      (영상④)
[4층] 행동        ← 에이전트: 생각→도구→관찰→반복       (영상②④)
[3층] 지식        ← RAG: 검색→증강→생성                 (영상③)
[2층] 입력 설계   ← 프롬프트 → 컨텍스트 엔지니어링      (영상②)
[1층] 엔진        ← 토큰 예측, temperature, attention    (영상②)
```

---

## [1층] 엔진 — LLM은 다음 토큰 예측기

- 입력 → 다음에 올 토큰 후보의 확률 → 하나 선택 → 반복.
- 확률적으로 고르기 때문에 같은 질문에도 답이 달라질 수 있다 = **비결정성**. temperature 낮으면 안정적, 높으면 다양.
- **비결정성은 창의성의 원천이자 프로덕션의 골칫거리** — "어제는 올바른 JSON, 오늘은 깨진 JSON"이 여기서 나온다. **뒤의 5층(검증·재시도)과 6층(평가)이 필요한 근본 이유.**
- 실전 감각: [rag_answer.py](https://github.com/hamjinoo/gongo-rag/blob/main/src/rag_answer.py)의 `TEMPERATURE = 0.2`는 "사실 기반이라 낮게"라는 이 층의 의사결정이다.
- 주의: 최신 API는 temperature=0이라도 완전히 동일한 출력이 보장되지 않는다.

## [2층] 입력 설계 — 프롬프트에서 컨텍스트로

- **프롬프트 엔지니어링** = 요청 문장을 잘 쓰는 것.
- **컨텍스트 엔지니어링** = 모델의 책상 위에 **어떤 자료를, 어떤 순서로, 얼마나** 올릴지 설계하는 것. 실제 입력은 시스템 지시 + 질문 + 이전 대화 + 검색 문서 + 도구 설명 + 출력 형식의 조립품이다.
- 핵심 질문: 무엇을 넣나? 무엇을 **빼나**? 어떤 순서로? 뭐가 더 신뢰할 만한가? 너무 많지 않은가?
- 이미 하고 있는 것: `PROMPT_TEMPLATE` + `build_context`(근거 번호 조립) + "정보 없음" 거절 규칙 = 컨텍스트 엔지니어링의 실물.

## [3층] 지식 — RAG

**폐쇄형 시험(암기) vs 오픈북 시험(찾아보고 답함).** 목적은 모델을 똑똑하게 만드는 게 아니라 **답하는 시점에 근거를 제공하는 것.**

```text
문서 수집 → 텍스트 추출 → 청킹 → 인덱스 → 질문 → 검색 → 컨텍스트 조립 → 답변 → 출처 검증
```
= gongo-rag의 extract_pdf → chunker → BM25/embedding → search → evaluate → rag_answer → verify_citation.

**"RAG는 죽었다" / "롱컨텍스트면 끝" 반박**: 문서를 통째로 넣으면 비용↑, 지연↑, 핵심 근거를 놓칠 수 있다. 컨텍스트 윈도가 커져도 **골라 넣는 검색은 여전히 중요.**

### 청킹 4종
| 방식 | 한 줄 | 비고 |
|---|---|---|
| 고정 길이 | N토큰씩 자르기(+겹침) | 쉽지만 문장이 잘림. 겹침(overlap)으로 경계 손실 방지 |
| 의미 기반 | 주제 바뀌는 지점에서 자르기 | 항상 더 좋은 건 아님 |
| **구조 기반** | 제목·번호목록·표 구조로 자르기 | **공고문처럼 구조 명확한 문서에 최적** ← 현재 방식 |
| 계층적 (parent-child) | 작은 자식으로 정확히 검색, 큰 부모로 맥락 제공 | small-to-big retrieval |

### 검색 3종
- **BM25**: 같은 단어 겹침. 숫자·고유명사·전문용어에 강함.
- **임베딩**: 의미를 벡터로. 표현이 달라도 뜻이 비슷하면 찾음.
- **하이브리드**: 둘을 융합(RRF 등). 어느 게 나은지는 **믿음이 아니라 측정으로** 결정. (로드맵 P1-C)
- 벡터 DB(Chroma 등)는 규모가 커질 때 필요. 학습 규모에선 NumPy 코사인으로 충분 — 제품 이름보다 검색속도/필터/규모/운영난이도가 본질.

### 10가지 RAG 패턴 = 체크리스트가 아니라 메뉴
| 패턴 | 한 줄 | 지금 나에게 |
|---|---|---|
| Simple | 한 번 검색 → 한 번 생성 | ✅ 현재 위치 |
| Memory | 이전 대화로 후속 질문 이해 (query rewriting 필요) | 나중 |
| Branched | 복합 질문을 하위 질문으로 분해·병렬 검색 | 3순위 |
| HyDE | 가상 답변을 만들어 그걸로 검색 (질문↔설명문 표현 차이 축소) | 나중 |
| Adaptive | 질문 유형별로 검색 방식 라우팅 | 2순위 |
| **Corrective** | 검색 결과 부족 판단 → 검색어 수정 → 재검색 | **1순위 — 평가 하네스가 있어야만 가능한 패턴. P1 완료 후 최적 확장** |
| Self-RAG | 생성 중간중간 스스로 검증 (원 논문은 전용 토큰 학습) | 개념만 |
| Agentic | 결과를 보고 다음 행동을 반복 선택 | Corrective의 확장 |
| Multimodal | 표·이미지·스캔 PDF까지 검색 | 나중 |
| Graph | 개체·관계 그래프로 다단계 관계 질문 | 공고문 QA엔 과함 |

**RAG vs Agentic RAG의 진짜 차이**: 프레임워크 사용 여부가 아니라 **"검색 결과를 보고 다음 행동을 선택하는 반복 구조가 있는가."**

## [4층] 행동 — 에이전트

> 모델은 생각하고, 에이전트는 생각한 뒤 **행동**한다.

- 구성 4요소: **LLM(두뇌) + 도구(손발) + 메모리 + 계획·추론.**
- 기본 루프(ReAct): `판단 → 행동 → 관찰 → 다시 판단` 반복.
- 패턴: **Reflection**(초안→검토→수정), **Plan & Execute**(계획 먼저), **Multi-Agent**(역할 분업).
- **멀티 에이전트 경고**: 수가 늘면 성능이 아니라 비용·지연·상태관리·전달오류·디버깅 난이도가 는다. 하나로 충분하면 하나로.
- **파이프라인 vs 에이전트**: 순서가 정해져 있으면 파이프라인/상태머신이 낫고, 상황 따라 다음 행동이 달라질 때만 에이전트. **"자율성과 구조 부재를 혼동하지 말라"** — 프로덕션일수록 통제 흐름이 명확해야 한다.

## [5층] 운영·통제 — 데모와 서비스의 차이

데모: `입력 → LLM → 출력`. 서비스: `검증 → 의도분류 → 모델선택 → 컨텍스트 → 도구선택 → 입력검증 → 권한 → 실행 → 확인 → 승인 → 답변 → 로그 → 평가`.

- **모델 라우팅**: 간단한 분류·추출은 작은 모델, 복잡한 판단은 강한 모델. (사담: JSON 구조화=Haiku, 장문 서술=Sonnet — 이미 실전 적용)
- **출력 계약**: 다른 코드가 받는 출력은 JSON 스키마로 고정 → 검증 실패 시 재시도 → 계속 실패면 폴백/중단. (로드맵 P2-B의 이론편, 사담의 스키마 검증+재시도가 실물)
- **도구 계약**: 도구는 엄격한 API — 이름/설명/입출력 스키마/권한/타임아웃/재시도/오류형식. `update_user("알아서 해줘")` 같은 모호한 도구 금지. MCP를 써도 이 계약·권한·로그의 필요성은 사라지지 않는다.
- **읽기/쓰기 분리 + 승인**: 조회(읽기)와 취소·결제·삭제(쓰기)는 위험이 다르다. `읽기 → 저위험 쓰기 → 고위험 쓰기+검증+사용자 승인` 순서로 개방. 안전 구조: `모델이 제안 → 코드가 규칙·권한 검증 → 사용자 승인 → 실행`.
- **상태 vs 메모리**: 상태 = 지금 작업이 어디까지 왔나(단계·승인 여부). 메모리 = 과거부터 무엇을 아나(선호·이력). 전부 벡터DB에 넣지 말 것 — 상태는 일반 DB/Redis, 지식 검색만 벡터 인덱스. **메모리 설계 = 데이터 아키텍처 설계.**
- **오케스트레이션**: 흐름을 통제하는 계층. LangGraph 등은 수단일 뿐 — 핵심은 **흐름이 명시적인가.**
- **비용·속도**: 요청 한 번에 모델 호출 여러 번. 작은/큰 모델 분리, 토큰 제한, 캐싱, 병렬화, 조기 차단, 비동기 평가. 지표는 API 비용이 아니라 **요청당·대화당·성공한 작업당 비용.**
- **보안 — 프롬프트 인젝션**: 위험은 사용자 입력만이 아니라 **검색된 문서·도구 결과·모델 출력**에서도 온다. 문서 속 "이전 지시를 무시하라"는 명령이 아니라 데이터로 취급. 명령/데이터 분리, 모델이 만든 SQL·쉘 직접 실행 금지, 최소 권한, 최소 개인정보.

## [6층] 척추 — 평가와 관측

**최종 답변만 보면 안 된다.** 문장은 자연스러운데 잘못된 문서를 검색했거나 잘못된 도구를 골랐을 수 있다 → 단계별로 평가 = **trace-level evaluation**.

```text
의도 분류 → 검색 품질 → 도구 선택 → 도구 입력 → 정책 준수 → 승인 → 최종 답변 → 작업 성공
```

지금 배우는 것이 정확히 이 척추의 앞부분:
- `hit rate@k` = 검색 단계 평가
- `verify_citation` = 근거·인용 단계 평가
- `groundedness` = 생성 답변 평가

**실행마다 남길 기록**: 모델·프롬프트 버전, 단계 이름, 검색 결과, 도구 입력, 지연, 토큰, 비용, 재시도, 폴백, 오류, 평가 점수. → "AI가 틀렸다"가 아니라 "어느 단계가 왜 틀렸다"를 말할 수 있게. (로드맵 P3의 이론편)

**테스트셋에 정상 질문만 넣지 말 것**: 모호한 요청, 범위 밖, 정보 일부만, 도구 실패, 악의적 입력, 정책 경계, 사람에게 넘겨야 할 요청. 모델·프롬프트·검색·스키마를 바꿀 때마다 이 셋으로 **회귀 테스트.** (로드맵 P1-E CI 게이팅)

# 내 프로젝트와의 매핑

| 지도의 개념 | 내 자산 / 로드맵 위치 |
|---|---|
| 골든셋 + faithfulness + CI 게이팅 | evaluate.py → P1-A, P1-E |
| citation 강제 / grounding | "정보 없음" 규칙 + verify_citation (P1-B) |
| 하이브리드 + 리랭커 | P1-C, P1-D |
| 구조화 출력 + 검증 + 재시도 | P2-B / 사담에서 실전 적용 |
| 모델 라우팅, 캐싱, 비용 관리 | 사담 (Haiku/Sonnet 라우팅) |
| 관측성, trace-level 평가 | P3 (Langfuse) |
| Corrective RAG | P1 완료 후 1순위 확장 |
