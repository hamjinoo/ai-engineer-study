# 09. 코드가 어려울 때 — 초보자를 위한 이해 프로토콜

> 읽는 시점: Week 1에 위치만 알아두고, **처음으로 "이 코드 뭔지 모르겠다"가 오는 순간** 다시 펴세요.

## 0. 먼저 안심 — 다 이해 못하는 게 정상입니다

경력 개발자도 남의 코드(그리고 6개월 전 자기 코드)를 다 이해하지 못한 채 일합니다. 초보자의 최대 함정은 모르는 것 자체가 아니라 **"100% 이해하기 전엔 다음으로 못 넘어간다"는 완벽주의**입니다. 그러면 Week 1에서 12주가 끝납니다.

핵심 원칙:

> **모든 코드를 같은 깊이로 이해할 필요가 없다.**
> 이해에는 단계가 있고, 파일마다 요구되는 단계가 다르다.

## 1. 이해의 3단계

| 단계 | 이름 | 기준 질문 |
|---|---|---|
| **1단계** | 실행 수준 | "이걸 돌리면 뭐가 나오는지 안다" |
| **2단계** | 라인 수준 | "각 줄이 무슨 일을 하는지 말할 수 있다" |
| **3단계** | 설계 수준 | "왜 이렇게 짰는지, 다르게 짜면 뭐가 문제인지 말할 수 있다" |

## 1-1. 퍼블리셔가 겪는 진짜 벽 — "무엇"이 아니라 "어디에/언제"

개념도 이해하고 손계산도 되는데 코드 앞에서 자꾸 막힌다면, 십중팔구 문제는 문법 지식이 아니라 **배치**입니다. 실제로 이 프로젝트에서 반복된 막힘들:

- `list = []`를 반복문 **안**에 넣어 매번 리셋됨
- `- overlap`을 슬라이스에 넣을지 range 간격에 넣을지
- `if f == 0`을 for문 **밖**에 써서 아직 없는 f를 참조함

셋 다 "무엇을 아느냐"가 아니라 **"어디에 놓느냐"** 예요. 재료는 다 아는데 "물 먼저? 면 먼저?"에서 멈추는 것 — 요리를 모르는 게 아니라 순서가 아직 손에 안 익은 겁니다.

**왜 퍼블리셔에게 유독 이 벽이 오나**: CSS는 *상태를 선언*하는 언어라 순서가 거의 상관없습니다(`color: red`는 위에 쓰나 아래 쓰나 빨강). 반면 파이썬은 *시간 순서대로 실행*됩니다 — `f`를 만들기 전에 `f`를 쓰면 에러, 준비물을 반복문 안에서 만들면 매번 초기화. **"먼저/나중"이 결과를 좌우**합니다. 이건 새 사고 회로라, 지금 헤매는 건 못해서가 아니라 그 회로를 만드는 중이라는 신호입니다.

### 뚫는 도구 — "밖 / 안" 두 칸 사고

코드를 쓰기 전에 각 줄에 질문 하나만 던지세요:

> **"이건 '한 번만' 하는 일인가, '매번(반복마다)' 하는 일인가?"**

- **한 번만** → 반복문 **밖** (예: 문서 꺼내기, 길이 재기, 보정값 계산, `total = 0` 빈 통 준비)
- **매번** → 반복문 **안** (예: 단어마다 개수 세기, 점수 계산, `total += ...` 누적)

BM25 `score()`로 예를 들면:
```
[한 번만 = for 밖]  이 문서 토큰 꺼내기 · 문서 길이 · norm(길이보정) · total=0
[매번   = for 안]  단어마다: f 세기 → f==0이면 continue → 기여 계산 → total에 더하기
```
`if f == 0`이 왜 for문 밖에 있으면 안 되는지 이제 자동으로 보입니다 — f는 "매번" 세는 값이니까요.

> 이 "밖/안 배치 감각"은 검색해도 안 나오고, 문법(`.count()`, `.get()`)과 달리 직접 짜봐야만 생깁니다. **개념만 아는 사람과 코드를 짜는 사람을 가르는 실력이 정확히 이것** — 지금 며칠이 그걸 만드는 시간입니다.

## 2-1. 코드를 읽는 순서 — main부터, 아래에서 위로

파이썬 파일은 위에서부터 읽고 싶어지지만, **실행의 시작점은 맨 아래 `if __name__ == "__main__":`(→ `main()`)** 입니다. 읽는 요령:

1. **main()부터** 읽고 "프로그램 사용 순서"를 문장으로 정리한다 — "불러온다 → 질문 받는다 → 검색한다 → 3개 출력한다"
2. 위쪽 함수들은 일단 **도구 상자**로 취급 — 안을 열지 말고 "이름 + 하는 일 한 줄"만 목록으로. (`load_chunks` = 파일을 chunk 리스트로 / `search` = 관련 chunk 골라줌)
3. 도구 상자를 여는 건 **그 도구가 이상하게 동작할 때뿐** — 예: 결과에 빈 chunk가 섞여 나오면 그때 비로소 `load_chunks` 안으로 들어간다 (증상 → 용의자 함수 → 해부. 이 순서가 디버깅의 정석이기도 합니다)
4. 읽으면서 각 줄 위에 **내 말로 `#` 주석 달기** — 주석을 못 달겠는 줄이 바로 "모르는 줄"이고, 그 줄만 아래 프로토콜로 처리하면 됩니다

> "위 함수들을 전부 해석해야 하나?" — 아니요. **main + 도구 목록**이면 오늘치 이해로 충분하고, 3단계(설계 수준) 이해가 필요한 파일은 2번 표에 정해져 있습니다.

## 3. 모르는 코드를 만났을 때 — 10분 프로토콜

순서대로. 대부분 3번 안에서 풀립니다.

1. **일단 실행한다.** `python 파일명`. 출력을 본다. (모든 파일에 `__main__` 데모가 있는 이유)
2. **출력 예측 게임**: 입력을 살짝 바꾸면 뭐가 나올지 **먼저 소리 내어 예측**하고 → 실행해서 확인. 맞으면 이해한 것, 틀리면 어디가 모호한지 정확히 드러남. (이해도 측정기)
3. **수술**: 입력을 아주 작게 바꾸고(문서 3개 → 문장 3개), 의심 지점마다 `print(f"{변수=}")`. 텐서/배열이면 무조건 `shape`부터.
4. **한 줄 격리**: 이해 안 되는 그 줄만 파이썬 셸(`python`)에 가져가서 장난감 값으로 재현. 예: `sorted(...) 이 줄이 뭐지?` → 셸에서 `sorted([("a",3),("b",1)], key=lambda x: x[1])` 쳐보기.
5. 여기까지 해도 모르면 → **질문한다** (아래 4번 — 죄책감 없이!).

## 4. "설명 요청"은 언제든 OK — 30분 룰 대상이 아닙니다

계획서 규칙을 다시 보세요: **개념 설명과 코드 리뷰는 "언제든 물어봐도 되는 것"**입니다. 30분 룰은 *디버깅*에만 적용됩니다. 금지는 딱 하나 — "내 대신 구현해줘".

다만 설명을 요청하는 방식에 따라 남는 게 다릅니다:

| 질문 방식 | 남는 것 |
|---|---|
| ❌ "이 코드 전체 설명해줘" | 듣는 순간엔 알 것 같고, 닫으면 사라짐 |
| ⭕ "큰 흐름을 3줄로 먼저. 그다음 12번 줄이 왜 필요한지" | 구조 → 디테일 순서로 쌓임 |
| ⭕ "이 줄을 **지우면** 무슨 일이 생겨?" | 존재 이유가 이해됨 (최고의 질문 유형) |
| ⭕⭕ "내가 이해한 걸 말해볼게: ~라고 이해했어. 틀린 곳을 짚어줘" | **파인만 기법** — 이게 면접 연습 그 자체 |

## 8. "직접 구현할 능력이 없는데?" — 가능합니다, 오해 하나만 풀면

> **한 줄 핵심: "직접 구현" ≠ "혼자서, 백지에서, 아무것도 안 물어보고". 금지는 딱 하나 — 완성된 답을 통째로 받는 것 — 이고, 조각을 묻는 건 전부 허용입니다.**

만약 "혼자 백지에서"라는 뜻이었다면 이 계획은 아무도 완주 못 합니다. 허용 범위를 정확히 보세요:

| GPT에게 이렇게 묻기 | 허용? | 이유 |
|---|---|---|
| "bm25.py의 TODO 구현해줘" | 🚫 | 완성품을 받으면 남는 게 없음 |
| "df가 정확히 뭘 세는 거야? 예시로 설명해줘" | ✅ | 개념 설명 |
| "dict에서 없는 키에 +1 하려면 어떻게 해?" | ✅ | 문법 질문 (BM25와 무관한 일반 패턴) |
| "set이 뭐야? 장난감 예제로 보여줘" | ✅ | 문법 질문 |
| "내 계획: ①토큰화 ②df 세기 ③평균 계산. 이 순서 맞아?" | ✅ | 접근법 확인 (코드가 아님) |
| "내가 짠 이 3줄에서 df가 이상해. 어디를 의심할까?" | ✅ | 내 코드 리뷰 |

**차이는 이겁니다: 조각(패턴)을 물어서 내 손으로 조립하면 실력이 남고, 조립된 완성품을 받으면 안 남습니다.**

### 실제 모습 — "df 세기" 60분 시나리오

1. bm25.py 힌트 4번을 읽는다: *"self.df = {단어: 등장 문서 수}. 함정: 한 문서에 10번 나와도 +1"*
2. (✅ 개념) "문서당 한 번만 센다는 게 무슨 뜻이야?" → 아, 문서 안 중복을 없애고 세는 거구나
3. (✅ 문법) "리스트에서 중복 없애려면?" → `set(리스트)`
4. [05-파이썬](05-파이썬-필수패턴.md)의 "빈도 세기의 정석" 패턴(`d.get(k,0)+1`)을 보고 3줄 시도
5. `python src\bm25.py` 실행 → 어라, IDF 값이 기대와 다름
6. (✅ 리뷰) "내가 짠 이 3줄에서 df(청년)이 3이 나와. 2가 나와야 하는데?" → "set을 안 씌웠네요"
7. 고침 → `python tests\test_bm25.py` → ✅ 통과

이 60분 동안 GPT가 4번 등장했지만 **조립은 전부 당신 손**이었습니다. 이것이 "직접 구현"이고, 3시간이 걸려도 정상입니다 (계획서가 오전을 통째로 준 이유).

### 안심 근거 — BM25에 "새로 배울 파이썬"은 없습니다

| 구현 조각 | 필요한 패턴 | 이미 있는 곳 |
|---|---|---|
| 문서들 토큰화 | 리스트 컴프리헨션 | [05 문서](05-파이썬-필수패턴.md) |
| df 세기 | `d[k] = d.get(k, 0) + 1` | 05 문서 — "빈도 세기의 정석" |
| avgdl | `sum(...) / len(...)` | 산수 |
| idf | `math.log(...)` 공식 그대로 | [BM25-완전정복](../04-concepts/BM25-완전정복.md) |
| score 합산 | `for` + `if` + `+=` | 기초 |
| search 정렬 | `sorted(..., key=lambda x: x[1], reverse=True)` | 05 문서 — "검색 랭킹의 핵심 한 줄" |

부족한 건 파이썬 실력이 아니라 **"어느 조각을 어디에 쓸지 고르는 경험"**인데, 그건 해봐야만 생깁니다. 그래서 12주가 있는 거고, 맞았는지 스스로 판단 못 해도 됩니다 — **테스트가 대신 채점해줍니다** (자가채점이 존재하는 이유).

### 그래도 완성 코드를 봐버렸다면 (현실적 사고 대처)

검색하다가, 또는 GPT가 묻지도 않은 코드를 보여줘서 답을 봐버리는 일은 생깁니다. 피해 최소화 프로토콜:

1. **복사-붙여넣기 금지.** 창을 닫는다.
2. 기억을 더듬어 **내 손으로 다시 타이핑** — 기억 안 나는 부분이 곧 "이해 못 한 부분"으로 정확히 드러납니다
3. 각 줄 위에 내 말로 `#` 주석 — 주석을 못 달겠는 줄은 개념 질문으로 되돌아가기
4. 테스트 통과 후, 파일을 덮고 **백지에서 한 번 더** (15분) — 이게 되면 진짜 내 것

"봤다"와 "베꼈다"의 차이는 손입니다. 눈으로 본 건 어쩔 수 없지만, 손이 기억하게 만드는 건 선택입니다.

## 9. "이게 AI 공부가 맞나? 파이썬만 하고 있는데" — 맞습니다

> **한 줄 핵심: Applied AI Engineer의 실무 = 파이썬으로 데이터·모델·평가를 다루는 일. 지금 그 시간이 직무 훈련의 본체입니다.**

- 업계 격언: "ML 작업의 80%는 데이터 작업" — 텍스트 자르기(chunking), 점수 매기기, 평가 코드가 곧 AI 엔지니어링입니다. `chunk_fixed`는 파이썬 숙제가 아니라 **RAG 파이프라인 ③단계 부품**이고, 면접 관문질문 1번의 재료입니다.
- 위험한 건 오히려 반대쪽: 개념은 아는데 코드로 못 옮기는 상태 — 과제·기술면접에서 가장 흔한 탈락 유형입니다. 계획서의 기준: *"많이 아는 사람이 아니라, 직접 만들고 실패를 설명할 수 있는 사람."*
- 이 마찰은 W1~3이 최고점입니다. 필요한 패턴은 6~7개뿐이라([05 문서](05-파이썬-필수패턴.md)) 손에 붙는 순간 뒤로 갈수록 빨라집니다. 첫 함수가 가장 느린 건 만국 공통 — 선불 투자 구간.
- 단, **잘못된 파이썬 시간**도 있습니다: 문법책 정주행, 파이썬 강의 새로 결제, 코딩테스트 문제풀이로 새는 것 (계획서 금지 항목). "프로젝트가 요구하는 패턴만, 필요한 순간에" — 이 방식이면 합격입니다.
