# 07. 헷갈림 FAQ — 여기서 다들 한 번씩 막힙니다

> 쓰는 법: 막히면 **GPT에게 묻기 전에** 여기 먼저. 이 목록에 없는 질문에서 막혔다면, 해결한 뒤 직접 추가하세요. (그 축적이 면접 대비입니다)

### Q1. "임베딩"이 두 군데 나오는데 같은 건가요?
**같은 개념, 다른 규모입니다.** 핵심은 둘 다 "이산적인 것(토큰/문장) → 의미를 담은 숫자 벡터".
- **tiny pretraining의 embedding layer**: 토큰 1개 → 벡터. 모델의 첫 층이며 **내가 학습시키는** 표(lookup table)
- **gongo-rag의 임베딩 모델**: 문장/chunk 전체 → 벡터 1개. 남이 미리 학습해둔 모델을 **가져다 쓰는** 것
- 면접에서 이 둘을 연결해 설명하면 "원리와 응용을 다 아는 사람"으로 보입니다.

### Q2. tokenizer(LLM)와 형태소 분석기(한국어 검색)는 뭐가 다른가요?
목적이 다릅니다.
- **LLM tokenizer** (BPE 등): 모델 입출력용. 의미와 무관하게 통계적으로 자주 붙는 글자들을 묶음. "지원금액은" → `지원/금액/은`이 아닐 수도 있음
- **형태소 분석기** (kiwi 등): 검색 매칭용. 언어학적 의미 단위로 자름 → 조사를 떼어내서 "지원금액**은**"과 "지원금액**이**"를 같은 것으로 만들어줌
- gongo-rag의 BM25에는 형태소 분석기를, tiny pretraining에는 문자 단위 tokenizer를 씁니다. 서로 대체재가 아닙니다.

### Q3. loss가 0이 되면 좋은 건가요?
**아니요, 오히려 경고등입니다.** train loss가 0 근처 = 훈련 텍스트를 통째로 암기했다는 뜻. 이때 validation loss는 보통 올라갑니다(overfitting). 우리가 원하는 건 암기가 아니라 **일반화** — 그래서 val loss를 같이 보는 겁니다. "train은 내리는데 val이 오르기 시작하는 지점"이 과적합의 시작.

### Q4. BM25도 "학습"을 하나요?
**안 합니다.** BM25는 단어 빈도(TF)와 희귀성(IDF)을 **세기만 하는** 통계 공식입니다. 파라미터를 조정하는 학습 과정이 없고, 그래서 데이터가 바뀌면 다시 세기만 하면 됩니다. "머신러닝 아닌 것도 검색에서는 여전히 강력하다"는 게 이 프로젝트의 첫 교훈입니다.

### Q5. RAG에서 검색을 LLM이 하는 건가요?
**아니요.** 검색(BM25/임베딩 유사도)은 LLM과 무관한 별도 코드이고, LLM은 **검색이 끝난 뒤** 결과를 받아 "읽고 답변을 작성"만 합니다. 여러분이 짜는 `bm25.py`, `embeddings.py`가 검색 담당, `rag_answer.py`의 API 호출이 생성 담당. 이 분리를 알아야 "검색 실패 vs 생성 실패"를 나눌 수 있습니다.

### Q6. 임베딩 검색에 쓰는 임베딩 모델도 LLM인가요?
사촌입니다. 같은 Transformer 계열이지만 **생성하지 않고 벡터만** 출력하도록 학습된 별도의 (보통 훨씬 작은) 모델입니다. 그래서 노트북 CPU에서도 돌아갑니다. "임베딩 모델 따로, 생성 모델(LLM) 따로" — RAG엔 모델이 2개 들어간다는 것.

### Q7. 왜 문서를 통째로 프롬프트에 안 넣고 chunk로 자르나요?
① 컨텍스트 윈도우 한계 ② 관련 없는 내용이 섞이면 답변 품질 하락 ③ 토큰 = 비용. 그리고 검색 관점에서: 30페이지짜리 덩어리 1개보다 문단 60개가 "질문과 딱 맞는 부분"을 집어내기 쉽습니다. → [03-RAG-기초](03-RAG-기초.md) 3번

### Q8. hit rate@3가 정확히 뭔가요?
골든셋 질문 30개 중, **정답 근거가 검색 결과 상위 3개 안에 포함된 질문이 몇 개인가**의 비율. 24개면 hit@3 = 0.8. "검색 단계만 따로" 채점하는 지표라서, 생성(LLM) 품질과 분리해 진단할 수 있게 해줍니다. 답변 자체의 품질 평가와는 다릅니다.

### Q9. 코사인 유사도 대신 그냥 내적을 쓰면 안 되나요?
벡터 길이가 전부 1로 정규화돼 있다면 **둘은 동일**합니다 (분모가 1이니까). 정규화가 안 돼 있으면 내적은 "긴 벡터"에 유리해져 왜곡됩니다. 실무 라이브러리들이 "normalize 후 내적"을 쓰는 이유. 직접 구현할 때는 cosine 공식 그대로 쓰는 게 안전합니다.

### Q10. GPU 없이 정말 되나요?
됩니다. tiny pretraining은 문자 단위 + 작은 모델이라 CPU로 몇 분이면 loss가 내려갑니다. gongo-rag의 임베딩 모델도 CPU로 문서 3개는 수 초~수십 초. GPU가 필요한 건 "큰 모델을 학습"할 때인데, 우리는 안 합니다.

### Q11. 벡터 DB(Pinecone 등) 없이 해도 되나요?
문서 3개(chunk 수백 개)면 numpy 배열로 전부 비교해도 밀리초 단위입니다. 벡터 DB는 벡터가 수십만~수억 개일 때의 도구. **"규모가 작아서 안 썼고, 커지면 이 지점에서 도입한다"고 말할 수 있는 게** 무작정 쓴 것보다 면접에서 강합니다.

### Q12. `loss.backward()`가 뭘 하는 건지 하나도 모르겠어요
"loss를 줄이려면 각 파라미터를 어느 방향으로 밀어야 하는지(기울기)"를 전부 자동 계산해주는 PyTorch 기능입니다. 미분을 직접 할 필요가 없습니다. 흐름만 기억하세요: `forward(예측·채점) → backward(방향 계산) → step(한 걸음 이동) → zero_grad(방향 초기화)`. → [사전훈련-원리](../04-concepts/사전훈련-원리.md)

### Q13. shape 에러 (`Expected ... got ...`)가 계속 나요
텐서 디버깅 제1원칙: **모든 줄 사이에 `print(x.shape)`**. tiny pretraining에서 알아야 할 shape는 사실상 세 개뿐입니다.
- `x`: (B, T) — 배치 B개, 각 길이 T의 토큰 ID
- `logits`: (B, T, C) — 각 위치마다 vocab C개에 대한 점수
- `cross_entropy`는 (N, C)와 (N,)을 원함 → 그래서 `view(B*T, C)`로 펴는 것
B=batch, T=time(길이), C=channel(vocab)이라는 관례만 익히면 에러 메시지가 읽히기 시작합니다.

### Q14. 답이 뻔히 문서에 있는데 검색이 못 찾아요
한국어 대표 원인 3가지를 순서대로 의심하세요.
1. **조사 불일치**: 질문 "지원금액은?" vs 문서 "지원 금액" → 공백 분리 BM25는 다른 단어로 취급 (형태소 분석으로 해결 — 6주차 실험)
2. **동의어**: 질문 "보조금" vs 문서 "지원금" → BM25 한계, 임베딩이 강한 영역
3. **PDF 추출 깨짐**: 정답이 표 안에 있어 텍스트가 조각남 → 검색 실패가 아니라 **데이터 문제**. `docs/text/`를 직접 눈으로 확인

### Q15. "정보 없음" 처리는 왜 그렇게 중요한가요?
실서비스에서 가장 위험한 건 **모르는데 아는 척하는 챗봇**입니다 (지원금 액수를 지어내면 사고). "근거에 없으면 정보 없음"은 환각 방어의 마지막 벽이고, 골든셋에 답 없는 질문 5개를 일부러 넣는 이유입니다. 면접에서 "품질을 어떻게 보장했나"의 답이 되는 부분.

### Q16. 학습 시작인데 loss가 이상해요 (너무 크거나 안 떨어짐)
체크 순서:
1. 시작 loss가 **ln(vocab 크기)** 근처인가? (65면 4.17) 아니면 구현 버그부터 의심
2. learning rate가 너무 큰가? (loss가 튀거나 NaN) → 1/10로
3. learning rate가 너무 작은가? (수천 step에도 변화 없음) → 10배로
4. 데이터가 실제로 섞여 들어가나? (`get_batch` 출력을 decode해서 눈으로)
5. `zero_grad()`를 빼먹었나? (기울기가 누적돼 이상 동작)

### Q17. 임베딩 모델은 뭘로 골라야 하나요?
시작은 `jhgan/ko-sroberta-multitask` (한국어 특화, 가볍고 무난 — 뼈대 코드의 기본값). 나중에 `BAAI/bge-m3` (다국어, 무거움) 같은 걸로 **바꿔서 hit@k를 비교하는 것 자체가 좋은 실험**입니다. "뭐가 최고냐"가 아니라 "내 데이터에서 비교해봤냐"가 취업 언어입니다.

### Q18. 프롬프트에 규칙을 썼는데 모델이 무시해요
① 규칙을 명령문으로, 번호 목록으로 (긴 산문 속 규칙은 잘 무시됨) ② 근거를 `[근거 1]`처럼 구조화 ③ temperature를 낮추기 ④ 그래도 무시하면 그 사례를 **생성 실패 케이스로 기록** — 고치는 것만큼 기록이 값집니다.

### Q19. 테스트가 ✅인데 왜 안심이 안 될 때가 있나요? (`all()`의 함정)
`all(조건 for x in 리스트)`는 **리스트가 비어있으면 무조건 True**입니다. 검사할 대상이 하나도 없으니 "전부 통과"라고 쳐주는 거예요 (`any()`는 반대로 빈 리스트에서 무조건 False). 그래서 함수가 버그로 **아무것도 안 만들고 빈 리스트를 반환**해도, `assert all(len(c["text"]) <= 300 for c in chunks)` 같은 검사는 속아서 통과해버릴 수 있습니다. 자기 함수를 테스트할 때든, 나중에 evaluate.py를 짤 때든, `all`/`any`를 쓰기 전에 **"결과가 진짜 비어있지 않은지"**부터 따로 확인하는 습관이 필요합니다 (`assert chunks` 한 줄 추가하기).
